## 一句话背景

给一台双臂人形机器人（每臂 7 自由度 + 剪刀式二指夹爪 1 自由度 + 腰 3 自由度）做抓取 VLA 的**选型 → 数据 → 训练 → 评估 → 真机部署**全链路，推理跑在服务器 GPU、通过网络与机器人上的 ROS2 客户端通信，成果面向开源发布。

**动作空间 16 维**（双臂 14 + 双爪 2），**状态 19 维**（再加腰 3，腰只观测不控制）。

## Part A — 选型

### Q1. 选型是具体怎么选的？

**不是读 README 比参数，是逐行读源码 + 实跑测量。** 四个维度，每个维度都有硬证据：

#### ① 图像预处理链路

读两家的图像变换实现，并实跑打印中间张量的实际尺寸：

| | π0.5 | GR00T N1.7 |
|---|---|---|
| 变换链 | 保宽高比缩放 → 补边到 224×224 | 最短边缩放 256 → 裁 0.95 → 再缩放 |
| 保宽高比 | ✅ | ✅ |
| **黑边浪费** | **25%**（4:3 输入 → 224×168 有内容） | **0%** |
| 输出尺寸 | 224×224 | 340×256 |
| 有效像素/相机 | 37,632 | **90,112（2.4×）** |
| token/相机 | 256（有效 192） | 88 |
| 横向 token 跨 FOV | **16** | 11 |
| 腕相机免几何增广 | ✅（刻意设计：腕相机刚性固连，几何本身编码末端位姿） | ❌（对所有视角同参裁剪） |

#### ② 参数高效微调可用性 —— **这一项是决定性的**

- π0.5 **有 LoRA**，官方显存表 22.5 GB → **单张 32GB 卡能完整迭代**
- GR00T N1.7 **无 LoRA**：整个模型目录 grep `lora` 零命中；N1 时代有过，1.5→1.6 被移除；动作头是 `bmm` 实现，连 peft 也包不住。碰视觉塔要 80GB+
- GO-1 的 LoRA **是死代码，调用即崩**

#### ③ 相机拓扑匹配度

π0.5 的图像槽位常量就是 `(base_0_rgb, left_wrist_0_rgb, right_wrist_0_rgb)`，源码注释明写「一个第三人称视角 + 两个腕视角」——**正是本体的头 + 左腕 + 右腕**。而官方参考任务里右腕槽位是补零的，我们三路全填真图，比官方例子更完整。

#### ④ 许可证

| 模型 | 许可 | 结论 |
|---|---|---|
| π0.5 (openpi) | Apache-2.0，骨干受 Gemma Terms（发布须随附） | 可用，一层义务 |
| GR00T N1.7 | NVIDIA OML + gated 骨干（需申请访问） | 可用，两层门禁 |
| GO-1 | **CC BY-NC-SA（非商用）** | 出局 |

#### 附加两项工程量判据

- **新本体接入代码量**：π0.5 约 150 行（官方参考文件全文 100 行且逐段注释写「复制这个类并修改」）vs GR00T 约 650–1250 行
- **官方先例数**：π0.5 有 2 个现成的数据转换脚本先例（其中一个是双臂的）；GR00T **零先例**

### Q2. 为什么最后是 π0.5 先做、GR00T 第二轨道？——顺便：我推翻过自己的初始结论

**这是选型过程里最值得讲的一段。**

**初始结论（拿到数据之前）是 GR00T 首选**，决定性理由是「腕相机是鱼眼 → GR00T 的图像链路不失真、π0.5 的补边会毁掉边缘视野」。

**真实数据到手后我做的第一件事是验这个前提**，结果它塌了：

- 腕相机的标定模型是 `plumb_bob`，**不是鱼眼**，实测畸变仅 **1.07%**
- 头相机确实是等距鱼眼（原始 FOV 172.1°×129.3°），但用数据自带标定做去畸变后**有效像素 100%、零黑边**，得到 127.7°×119.5° 的真针孔图

**「鱼眼 × 显存」这一轴一塌，GR00T 的图像优势从决定性降为边际，剩下的比较项一边倒向 π0.5** → 改为 π0.5 先做。

**回头切 GR00T 的触发条件也一并写清了**（避免选型变成一次性拍板）：
1. π0.5 的 25% 黑边或动作维补零被 A/B 证明伤性能
2. 要喂超过 3 路相机（π0.5 只有 3 个槽位）
3. 要用 GR00T 的高维状态余量喂腰/头/IMU
4. 要官方离线评估与 ONNX/TensorRT 部署链路

### Q3. 为什么 GO-1 出局？公司已有 GO-1 生态，为什么不直接用？

出局是**五条独立理由叠加**，任一条单独不足以否决：

1. **许可证 CC BY-NC-SA 非商用**——可以争取 relicense，但**员工身份不自动豁免 NC**，而项目要求「保留商用可能」
2. **LoRA 是死代码，调用即崩**——直接决定它只能全量微调
3. 鱼眼图默认被各向异性拉伸
4. 读过的 **14+ 个 issue 零官方回复**
5. 本机未跑通（环境缺依赖、权重未提供）

**唯一的真优势**：官方 checkpoint 的动作维度就是 16 维，与本体精确相等。这一条我如实记下了，没有为了结论好看而隐去。

至于「为什么不直接用自家生态」——这个问题本身就是立项时定的调研任务：需求是**给出选型与迁移工作量的横向对比后再定**，而不是默认用自家的。

### Q4. 「5 个基座」都有哪些？各自一句话淘汰理由

| 基座 | 结论 | 一句话理由 |
|---|---|---|
| **π0.5 (pi05_base)** | **首选，已落地** | 有 LoRA、相机拓扑天然对齐、有同构官方参考配置、零访问门禁 |
| **GR00T N1.7** | **第二轨道，已落地** | 图像链路更干净、预训练本体里有双臂 7-DoF+腰的同构平台；但无 LoRA |
| GO-1 | 出局 | 非商用许可 + LoRA 死代码（见 Q3） |
| RDT-2 | 备查 | 官方 README 示例代码有 4 处硬伤照抄跑不通；定位是 zero-shot 跨本体，与主线不同 |
| UnifoLM-VLA-0 | 否决 | 综合能力弱于同期同类 |

## Part B — 两条微调—部署链路

### Q5. 「打通微调—部署链路」具体指什么？

指从原始日志到机器人动起来的**六个环节全部自己接通**，不是只跑了训练：

```
① 原始 protobuf 日志（含图像/关节/指令，多路相机）
   ↓ 自写转换：动态解析 schema、按标注裁剪、丢帧处切段、统一视频编码
② 标准模仿学习数据集（LeRobot 格式）
   ↓ 自写输入/输出变换 + 数据配置 + 训练配置
③ 归一化统计量（独立步骤，缺了训练会显式报错）
   ↓ LoRA 微调
④ checkpoint
   ↓ 官方 policy server（零改动）
⑤ 策略服务（网络端点）
   ↓ 自写 ROS2 客户端，把真机包装成标准环境接口
⑥ 机器人执行
```

**每个箭头都有具体产出物**：转换脚本、变换类、训练配置条目、复位姿态计算脚本、ROS2 客户端、RTC 调度器。

### Q6. 两条链路各自的接入工作量？为什么完全独立、不共享代码？

#### π0.5 侧

- 输入/输出变换类（约 100 行）：把原始 179 维状态切成 19 维、把 97 维动作切成 16 维、三路图填进模型的三个图像槽位
- 一个数据配置工厂 + 一个训练配置条目
- **踩过一个静默陷阱**：框架里有个现成的双臂数据配置看着完全适用，但它默认开一个「适配某款特定机器人」的开关，会做**关节符号翻转**（第 2/3 号关节取反）+ 夹爪值域重映射。**用了不报错，只是训练全废。** 正确做法是复制那个 docstring 明写「复制这个类」的通用配置

#### GR00T 侧

- **零核心包改动**：它的 launcher 用动态导入加载配置文件，所以新本体的东西全部落在示例目录下
- 一个 modality 配置（对扁平列做区间切片 → **数据集零重转**）
- 一个自写 launcher，只为了透出官方 CLI 够不到的两个字段

#### 为什么完全独立

**两条轨道最终是两个仓库、两个分支，任一条要能单独交付。** 所以 GR00T 侧的部署客户端：

- 不许 `sys.path` 指向另一个仓库
- **也不许 import 另一条链路用 pip 装的 client 包**——那是同一种耦合，只是过了一层 pip

代价是下标常量有三份副本，改一处要同步。这是明确接受的代价。

### Q7. 动作空间为什么是 16 维？为什么臂相对、爪绝对？

#### 16 维的来源

本体在动的自由度是 31 维（12 腿 + 3 腰 + 14 臂 + 2 爪）。抓取任务只控**臂 + 爪 = 16 维**；腰进状态不进动作（它在数据里是活的，但让模型控腰会在数据量小时引入不必要的自由度）。

#### 「臂相对、爪绝对」是从数据分布推出来的，不是抄配方

**夹爪必须绝对量**，依据是全量帧统计：

```
夹爪指令值的分布：
  恰好 1.0（全开）: 81%
  恰好 0.0（全闭）: 12%
  中间过渡值      : 6.6%
```

这是一个**双峰二值信号**。做成相对量（增量）的话，绝大多数帧的增量恰好为 0 → 模型会学成「永不动爪」。

**臂用相对量**（相对当前测量姿态的增量），与预训练权重的口径一致。

实现上就是一个布尔掩码：

```
delta_mask = 前 14 维 True（相对） + 后 2 维 False（绝对）
输入侧: DeltaActions(mask)     # 训练时把绝对动作转成增量
输出侧: AbsoluteActions(mask)  # 推理时把增量加回当前状态
```

GR00T 侧是等价的四个动作配置：`[RELATIVE, RELATIVE, ABSOLUTE, ABSOLUTE]`（左臂、右臂、左爪、右爪）。**两条链路的这个决定必须一致，否则横向对照没有意义。**

### Q8. 数据是怎么进模型的？

原始数据是**稀疏布局**：179 维状态 / 97 维动作，其中大部分维度恒为 0。**并且状态和动作的同一个关节组下标不同**——这是最容易搞错的地方：

| 关节组 | 在 action 里 | 在 state 里 |
|---|---|---|
| 双臂（14） | `[59:73]` | `[45:59]` |
| 腰（3） | `[39:42]` | `[36:39]` |
| 双爪（2） | `[95:97]` | `[95:97]` ← 只有这个恰好相同 |

```
# 输入变换（伪代码）
state_19 = concat(state[臂], state[爪], state[腰])   # 腰必须放最后
action_16 = concat(action[臂], action[爪])
image = {头: 头相机, 左腕: 左腕相机, 右腕: 右腕相机}
```

**「腰必须放最后」不是风格问题**：相对/绝对掩码是按位置对齐的，腰若插在中间会让掩码错位——而且不报错。

**这些下标是自己反推的，不是文档给的。** 反推方法：全量帧统计哪些维度在动（结果：只有 31 维在动，其余 63 维恒 0），再逐段用相关性和取值范围锁定语义。有一处曾判错——腰的下标单帧看像 `[37:40]`，6258 帧全量统计才证明是 `[39:42]`。

**顺带验证了一件必须验的事**：`action` 不是 `state` 的回读（否则训练信号是废的）。6258 帧全量比对臂块，**最大差 10.29°，完全相等的帧 0/6258**。

## Part C — 训练与评估

### Q9. 单卡 32GB 怎么跑起来的？

- 卡是 RTX 5090（32GB）
- **LoRA + 关掉 EMA**：官方注释要求 LoRA 时必须关 EMA（否则显存翻倍且无意义）
- batch=8 峰值 **20.7 GiB**
- 3000 步，**loss 0.475 → 0.0125（降 38 倍）**，1725 步后进平台期
- 动作维度必须留框架默认的 32（16 维靠补零）；改成 16 会因严格 shape 校验直接报错

#### 踩过的架构坑，以及从中得到的可迁移结论

新架构（Blackwell / sm_120）上 **PyTorch 必须用对应 CUDA 版本的 wheel**，否则报「no kernel image」。关键教训：

> **`torch.cuda.is_available() == True` 不能作为验证通过的证据**——它只查驱动认不认卡，不查编译进 torch 的 kernel 含不含这个架构。必须真跑一次 CUDA 算子，或者看架构列表里有没有对应项。

**但这条规则不通用**：JAX 走 PTX JIT，同一张卡上社区报的编译器版本问题**不复现**，实测端到端 10/10 步通过、日志里有 cuDNN 算子调优记录（确认真用了 GPU 不是 CPU 回退）。

> **不要拿一个框架的判据去误判另一个框架。**

#### GR00T 侧的显存实测（推翻了「必须上云」的前提）

| batch | 峰值显存 |
|---:|---:|
| 1 | 27.55 GB |
| 4 | 28.57 GB |
| **8** | **29.37 GB ← 推荐** |
| 16 | 32.03 GB（只剩 0.6GB 余量，不可用） |

batch 8 稳态 **1.2 steps/s**，配梯度累积 4 = 有效 batch 32（与云端配方等价），**10000 步约 2.3 小时**。云端只在要解冻视觉塔（需 80GB+）时才必需。

### Q10. 「含零位移基线的开环评估」是什么？为什么必须有基线？

官方**没有**离线评估脚本，自己写的。核心设计是那条 baseline：

```
# 零位移基线（trivial baseline）
baseline_prediction[k] = 当前状态           # 对所有 k：预测「什么都不动」
model_prediction[k]    = 模型输出的第 k 步

MAE_model    = mean(|model_prediction − ground_truth|)
MAE_baseline = mean(|baseline_prediction − ground_truth|)
```

**为什么必须有它**：MAE = 1.41° 这个数字**单独存在时无法解读**。抓取任务里大量帧的位移本来就很小，一个什么都不预测的常量函数也能拿到很低的 MAE。**没有基线，你不知道 1.41° 是模型学到了东西，还是任务本身就简单。**

#### 实测结果

| | 训练集（26 条） | 验证集（2 条） |
|---|---|---|
| 双臂 MAE | 0.92° | **1.41°** |
| 零位移基线 MAE | 2.48° | **2.68°** |
| 倍数 | 2.70× | **1.90×** |
| 夹爪二值准确率 | 0.995 / 0.990 | 0.991 / 0.995 |

验证集显著优于基线 → **数据处理与接入链路正确，模型确有泛化、不只是记忆**。

#### ⚠️ 数据来源要说清

**这组数字来自第一批给定数据（29 条，26 训 / 2 验），不是后来自采的 60 条那批。** 自采那批是全量进训、没切验证集（明确的决策，见 Q13）。被问到时不要混。

### Q11. MAE 1.41° / 优于基线 1.9 倍怎么读？它等于抓取成功率吗？

**不等价，这一点要主动说。** 三层限定：

#### ① 它是全 chunk 平均，真实策略误差更低

报的 MAE 是对整个动作块求平均。但实际推理**不会用完整个块**——只截取前几步（误差最小的部分）就重新推理。所以真实策略的有效 MAE 比 1.41° 更低。

进一步量到：**误差随预测步长增长 5–7 倍**。

#### ② 低位移区这个指标没有分辨力 —— 这是方法论级的发现

现象：**在位移小的关节/帧上，模型「赢不过」零位移基线。**

第一反应会判成「模型在静止段学废了」。但拟合出来的关系是：

```
模型误差 ∝ 位移^0.39
```

指数 0.39 < 1，意味着**位移趋于 0 时模型误差也趋于 0，只是下降得比位移本身慢**——不是一个恒定的误差地板。

推论：**低位移区输给基线是指标本身分母太小造成的，不是模型能力缺陷。** 如果不做这个拟合，就会得出「模型在静止段有问题」的错误结论并去做无用的修补。

#### ③ 数值精度 ≠ 任务成功

MAE 衡量的是动作预测的数值精度。抓取成功还取决于：闭环纠错能力、视觉泛化、夹爪时序。**这两者可以背离。**

### Q12. 抓取成功率是多少？

**能抓到，但没有系统性统计成功率。** 诚实的现状：

- 真机推理可以完成抓取动作
- **但失败模式已经归类清楚了**（见 Q24），主要是站位变化与物体侧向位置
- 成功率统计需要固定协议下的 N 次重复试验，而当时正在重采数据以消除已知失败因子，统计一个即将被推翻的版本的成功率没有意义

**这是这个项目当前最大的短板**，被问到时直说，并接上「所以下一步是重采 100 条覆盖式数据后再统计」。

### Q13. 验证集只有 2 条，够吗？

**不够，这是已知不足。**

- 第一批数据 28 条可用 → 26 训 / 2 验（左右手各一条，刻意保证两种手别都被覆盖）
- 2 条验证集只够回答「链路对不对、有没有完全过拟合」，**不足以做模型选择或早停**
- 更严重的是：**后来自采的 59 条是全量进训、没切验证集**（用户明确决定）→ 那一批的离线数字只能当「训练集拟合程度」读，**不是泛化指标**

**这个短板的成因是数据总量太少**（3.5 分钟 / 12223 帧，官方推荐每任务 100–200 条），切验证集的边际代价太高。正确的解法是先把数据量做上去。

## Part D — 部署

### Q14. 「策略服务标准接口」是怎么样的？

把真机实现成推理框架定义的 `Environment` 抽象，**服务端一行不改就能接**：

```
class X2Environment(Environment):

    def reset():
        # 1. 等观测新鲜（臂/腰/爪都要在各自阈值内更新过）
        # 2. 查运控模式，必须是「全身操作」模式，否则断言失败
        # 3. 时钟偏差必须已测出（见 Q18），否则拒绝下发任何指令
        # 4. 核对腰是否在训练数据覆盖范围内，不在就要求操作员摆回去
        # 5. 按固定角速度插值把臂平滑摆到复位姿态，等伺服收敛
        # 6. 等三路相机就绪
        pass

    def get_observation() -> dict:
        # 断言：所有话题都在各自的过期阈值内
        # 断言：关节组无域级故障（下电/掉使能/CAN 断连）
        # 断言：夹爪无故障码（过温/超速/初始化/超限）
        # 组装成 179 维稀疏 state + prompt + 三路图
        pass

    def apply_action(action):
        # 只更新「目标」，不直接发布（发布由独立定时器做，见 Q15）
        # 臂钳到关节限位、爪钳到 [0,1]，并累计被钳次数
        # 每步落一条 JSONL（state / action / 钳制次数 / 夹爪硬件状态 / 时钟偏差 / RTC 饥饿计数）
        pass

    def is_episode_complete() -> bool:
        return False   # 本任务没有可靠终止信号，跑满步数上限
```

主循环由框架的 Runtime 驱动：`get_observation → agent.get_action → apply_action`。

#### 这个边界划对了的证据

原计划写的是「GR00T 侧要复制客户端并改三处（传输 / 观测格式 / 动作格式）」。实际核对后**三处都不用改**：

| 计划说要改 | 实际情况 |
|---|---|
| 传输 | 传输本来就不在 Environment 里，写个新入口就行 |
| `get_observation` | 返回的扁平 179 维状态已含全部分组，能拆得出 |
| `apply_action` | 已收 16 维**绝对**量，而 GR00T 的相对→绝对转换在服务端完成 → 口径本来就一致 |

**适配层可以整个塞在 Environment 之上**，ROS 边界以下（订阅、QoS、时钟补偿、复位斜坡、限位钳、故障码、日志、重发定时器）一行不用动。

#### 额外收益：回放模式

服务端可以换成**喂数据集而不是 checkpoint**（回放真值动作），**客户端代码零改动** → 训练还没好就能先把 ROS 客户端整条链路跑通。这也是后来做开环回放验证的基础（见 Q22）。

### Q15. 为什么 30Hz 推理 / 50Hz 下发要解耦？

```
主循环（30Hz，与数据采集帧率对齐）:
    obs ← get_observation()
    action ← agent.get_action(obs)     # 可能触发推理，有长尾
    apply_action(action)                # 只写「目标」变量

独立定时器（50Hz，另一个线程）:
    publish(最新目标)                    # 不管推理在不在跑
```

**如果指令跟着推理频率发**，推理一旦有长尾（偶发几百毫秒），下游会看到话题静默 → 触发超时保护 → 机器人停住甚至进保护状态。

**解耦后**推理卡住期间定时器仍以 50Hz 重发上一个目标，链路始终活着。

**代价要说清**：卡住期间是**开环**（一直重发同一条陈旧指令）。所以配了饥饿计数与硬停机（见 Q16）。

### Q16. RTC 异步预取具体怎么实现的？

实现的是论文（arXiv 2506.07339）的**客户端侧**：异步预取 + 上一块引导对齐。

#### 三个参数

| 符号 | 含义 | 取值 |
|---|---|---|
| **H** | prediction horizon，模型一次输出多少步 | 32 |
| **s** | execution horizon，执行多少步就换块 | `max(d, H/2)`，H/2 是下限不是定值 |
| **d** | 推理延迟折算的步数 | `ceil(max(近 10 次延迟) × 控制频率)` |

**d 取近 K 次的 max 而不是均值**——长尾才是危险的。**首块耗时不计入延迟窗口**（首次调用含 JIT 编译，不代表稳态）。

#### 两条不变量（违反即断言失败，不静默降级）

```
d ≤ s        # 新块到达时前 d 步确实已执行完 → 那 d 步被硬冻结，不能再改
s ≤ H − d    # 旧块剩余长度够覆盖推理期间
```

#### 主流程伪代码

```
每个控制步:
    if 后台推理已完成:
        chunk ← 新块
        t ← t − s                       # s = 发起那次推理时已执行的步数
        饥饿连击 ← 0

    d ← 延迟折算步数()
    触发点 ← max(d, s_min)
    if 没有进行中的推理 and t ≥ 触发点:
        prev ← chunk[s:] 左移后右侧补零   # 旧块剩余部分作为引导传给服务端
        异步启动 推理(obs, prev, s, d)

    if t ≥ H:                            # 新块没赶上
        饥饿计数 += 1; 饥饿连击 += 1
        assert 饥饿连击 ≤ 60              # 2 秒。再撑就是长时间开环，停机更安全
        return chunk[-1]                  # 沿用最后一步（下游定时器本就在重发）

    a ← chunk[t]; t += 1
    return a
```

#### 服务端侧的引导权重

服务端拿到 `prev`（上一块剩余）和 `(s, d)` 后计算逐步混合权重：

```
i ← 0..H-1
c ← (H − s − i) / (H − s − d + 1)
w ← c · expm1(c) / expm1(1)
# 前 d 步权重最大（硬冻结区），往后单调衰减到 0
```

**饥饿计数会落进每步的 JSONL 日志**，所以事后能定量看有没有饥饿、饥饿几次。

### Q17. ⚠️ RTC 是否验证了抖动改善？

**没有。这是实现完成但效果未量化的一项。**

准确的现状：

- ✅ 实现完成，两条不变量有断言保护，饥饿有计数与硬停机
- ✅ 离线自检通过（形状、时序、触发次数）
- ❌ **真实推理延迟还没量**——量它需要一个训好的 checkpoint 起模型服务，而 base 权重起不了新本体的服务
- ❌ 因此「抖动减少了多少」**没有数字**

**该怎么答**：「抖动是 8/19 真机推理时观测到的现象，RTC 是针对它的措施，也是论文里对这个问题的标准解法，但我还没有前后对照的量化数据——量它需要先测出真实推理延迟。」

**不要说成已验证。** 这是全篇最容易被问穿的地方之一。

### Q18. 时钟偏差补偿是怎么做的？

#### 问题

上位机（跑客户端）和下位机（跑运控）时钟不同步。下游用 `接收时刻 − 指令时间戳 > 200ms` 判定指令陈旧并丢弃。**时钟偏差一旦超阈，所有指令被静默丢弃——机器人不动，且不报错。**

#### 做法：不做时钟同步，而是让误差方向恒为「保守」

```
# 订阅回调（关节状态 500Hz）
on_arm_state(msg):
    skew ← 本机now() − msg.header.stamp      # 持续测量
    skew_window.append(skew)                  # 保留约 1 秒的样本用于抖动检查

# 发布（50Hz 定时器）
publish_target():
    t ← 本机now() − skew                      # 换算到机器人时钟域
    msg.header.stamp ← t
```

#### 为什么这样是安全的（完整推导）

设：
- `H` = 上位机发送那一刻**自己表**的读数
- `Δ` = 上位机表 − 下位机表（所以 下位机表 = 上位机表 − Δ）
- `d↑` = 下位机 → 上位机 的单向传输延迟
- `d↓` = 上位机 → 下位机 的单向传输延迟

则测出的 `skew`（在订上关节状态那一刻起持续测量的值）：

```
skew = Δ + d↑
```

上位机写进时间戳的数字：

```
stamp = H − skew = H − Δ − d↑
```

下位机收到时算出的「年龄」：

```
年龄 = 接收时刻 − stamp
     = (H − Δ + d↓) − (H − Δ − d↑)
     = d↑ + d↓
```

**关键结论**：

```
d↑ + d↓ > d↑     恒成立
```

算出的年龄**永远大于**真实的单向延迟。所以拿它和 200ms 阈值比较是**保守安全的**：

- 只可能把新鲜指令误判为陈旧（宁可丢）
- **绝不会把陈旧指令判成新鲜**（这才是危险方向）

> **要点是「误差方向单侧」，而不是「误差小」。** 这是这个方案的全部价值——它不需要任何时钟同步基础设施，只需要保证犯错的方向是安全的那一侧。

#### 配套的三道检查

| 检查 | 阈值 | 目的 |
|---|---|---|
| 时间戳恒为 0 | 断言失败 | 测不出偏差就绝不下发指令 |
| 近 1 秒样本极差 | > 20ms 告警 | 偏差在抖 → 网络或时钟不稳 |
| 偏差绝对值 | > 1s 告警 | 补偿后不影响控制，但机器人侧日志时间戳会难对齐 |

**这三道都在 `reset()` 里、在下发任何指令之前**。

### Q19. 复位是怎么做的？为什么复位姿态用 medoid？

#### 为什么复位这么重要

**这是实机两条安全门之一。** 臂是相对量动作，基准是当前状态——**偏出训练分布的初始位姿全都是合法关节角**，下位机的软限位和速度限都不会报错，机器人只是**平滑地走到一个错的地方**。这个失败是完全静默的。

#### 复位姿态怎么算的

```
输入：训练集所有 episode 的首帧姿态
臂 / 爪 ← medoid（到其余所有首帧总距离最小的那一条真实首帧）
腰      ← 逐维中位数
```

**为什么臂用 medoid 而不是逐维中位数**：首帧是**多模态分布**（不同起始位置、不同手别），逐维取中位数会落在流形的「洞」里——一个每一维都合理、但整体从未出现过的姿态。**medoid 本身就是一条真实训练样本，到训练分布的距离恒为 0。**

**腰可以用中位数**，因为它是「核对当前姿态用的参考点」，不是要摆过去的目标。

#### 容差

- **臂**：固定收敛容差（5°），不由数据 std 决定——它是伺服收敛判据，不是分布描述
- **腰**：全量帧实际覆盖范围撑出的最小对称盒 + 1° 余量

**踩过一个坑**：算「复位姿态离训练流形多远」时，参考集必须是**全量帧**。用抽稀（stride=5）会人为拉大近邻距离——实测让 P99 从 13.3° 变成 39.5°，结论完全错。

#### 执行

```
_ramp_arm_to(target):
    span ← max|target − 当前|
    duration ← span / 15°每秒        # 固定角速度，不是固定时长
    在 duration 内线性插值更新「目标」变量
    # 实际发布仍由 50Hz 定时器做

_wait_arm_converged():
    轮询直到 所有关节残差 ≤ 容差，或超时 15s
    # 关键：同时记录「实际走了多少度」
    # 收敛且走了 > 0.5° → 指令确实被执行了
    # 收敛但一动没动    → 起始就在容差内（不能算验证通过）
    # 超时且动过        → 指令收到了但跟不上
    # 超时且没动        → 指令没被执行 ← 这是最需要区分出来的情况
```

**最后那个四分支是刻意的**：「臂到位了」和「臂根本没动但恰好本来就在位」在日志里必须能分开，否则会把「指令通道不通」误判成「复位成功」。

### Q20. 实机安全怎么保证的？为什么只有两条安全门？

**安全门从最初列的 7 条砍到了 2 条**，上榜判据是：**① 失败是静默的 ② 没有别的层能兜住它**。

#### 保留的两条

1. **初始位姿必须在训练分布内**（理由见 Q19）
2. **人在急停上**

#### 砍掉的，以及为什么

| 曾列为安全门 | 为什么砍掉 |
|---|---|
| 客户端钳关节限位 | 下位机已有 `关节软限位超限` / `位置超限` 错误码，客户端钳只是第二道（仍保留代码，但不算安全门） |
| 客户端钳速度/加速度 | 下位机已有 `速度超限` / `加速度超限` 错误码 |
| 首轮禁用夹爪 | **夹爪是模型最可靠的一维**（二值准确率 0.991/0.995，高于任何臂关节）；禁掉反而测不到抓取 |
| horizon 对齐 | 属正确性问题，不属安全门 |

> **判据是「失败是否静默」，不是「后果是否严重」。** 有错误码兜着的项，即使后果严重，也不该占用安全门的注意力预算——注意力应该给那些错了完全没有反馈的项。

## Part E — 故障归因

### Q21. 「真机动作幅度坍塌至 0.3 倍」是怎么定位为观测域分布偏移的？

#### 现象

真机推理表现为「**起步正确但不敢展开轨迹**」——动作方向对，但幅度明显偏小，够不到物体。

这类现象的嫌疑人很多：机器人本体、底层运控、客户端实现、模型本身、训练数据。

#### 做法：构造一张可对照的量化表

**关键设计**：抓**模型的原始输出**，在任何下发钳制之前；对三种观测来源跑同一套推理；沿预测步长展开。

```
for source in [训练集, 验证集, 真机]:
    obs   ← 从该来源取观测
    chunk ← 模型原始输出(obs)              # 钳制之前
    for k in [0, 5, 10, 15]:
        幅度[source][k] ← max over 14 维 |chunk[k] − 当前状态|

对照 幅度[真机][k] / 幅度[验证集][k]
```

#### 结果（单位：度）

| 帧 k | 训练集 GT | 训练集推理 | 验证集 GT | 验证集推理 | **真机推理** | **真机/验证集** |
|---|---|---|---|---|---|---|
| 0 | 0.83 | 0.98 | 0.77 | 0.76 | 0.95 | 1.25× |
| 5 | 5.14 | 5.50 | 4.54 | 5.47 | 1.65 | **0.30×** |
| 10 | 12.31 | 12.95 | 11.72 | 12.63 | 3.30 | **0.26×** |
| 15 | 19.89 | 19.99 | 19.24 | 18.71 | 6.02 | **0.32×** |

#### 这张表一次排掉三个嫌疑人

| 嫌疑人 | 排除依据 |
|---|---|
| 模型本身 / 训练配方 | **验证集推理不坍塌**（18.71 vs GT 19.24） |
| 机器人本体 / 底层运控 | 抓的是**模型原始输出**，在下发之前，机器人还没参与 |
| 「模型整体学废了」 | **k=0 时正常（1.25×）**，k 增大才塌 → 精确对应「起步对、不敢展开」的观测 |

**剩下的只有：真机的观测和离线数据不一样。**

进一步在**姿态匹配口径**下复核（控制住起始姿态这个变量）：离线 1.01× / 0.97×，真机 0.32× → **幅度坍塌只在真机观测下发生**，结论更硬。

#### 再做消融，确认单一视觉因素不足以解释

| 消融 | 是否复现坍塌 |
|---|---|
| 换 prompt（占位符 / 两种正经指令，共 3 种） | ❌ |
| 图像与姿态故意错配（第 100 帧的图配第 500 帧的关节） | ❌ |
| 调亮度、对比度（模拟现场光照差异） | ❌ |
| 整张图置零（全黑） | ❌ |
| 随机噪声图 | ❌ |

**没有一个能复现** → 不是某个单一的图像扰动因子，而是观测的整体分布偏移 + 数据量不足。

### Q22. 怎么排除客户端实现的？

Q21 把嫌疑收窄到「观测域」，但客户端仍未被正式排除——它经手了观测和动作两侧，理论上可能在某一侧做了缩放。

#### 做法：实机开环回放

**不接模型**，直接把数据集里的真值动作喂给客户端下发，然后抓下游实际收到的命令，做**逐帧逐字节比对**。

```
for 帧 i in 数据集 episode:
    apply_action(数据集真值动作[i])
    记录 下游实际收到的命令[i]

比对: 下游命令 vs 数据集真值   # 逐字节
检查: 时间上有没有滞后
```

#### 结果

- **臂命令 126/126 帧逐字节等于真值，滞后 = 0**
- → 客户端在 ROS 边界以下的实现被彻底排除

#### 一个反直觉的细节（值得讲）

回放时观察到夹爪「合得比数据里更紧」，看着像 bug。查下来是**物体厚度**导致的——夹爪测量值停在 110/255，而指令是全闭。

**这反而反证了回放是忠实的**：如果回放不忠实（比如指令被缩放了），测量值不会恰好卡在物体厚度对应的位置上。

> 一个看起来像 bug 的观测，查清机制后可能是正确性的证据。不要看到差异就改代码。

### Q23. 观测域偏移的根因最终找到了吗？

**找到了，但闭环修复当时还在进行中。**

#### 根因

**部署用的机器与采训练数据的机器不是同一台**（机身序列号不同）。

#### 最硬的证据

**腕相机拍自己的夹爪，尺度差 1.45 倍。**

夹爪是刚性固连在腕相机视野里的已知物体——它在图像里的大小完全由相机内参和安装位置决定。**1.45 倍的尺度差意味着这两台机器的腕相机标定/安装存在实质差异。** 模型在 A 机的视觉分布上训练，在 B 机上推理，等于跨了一次小型的本体迁移。

#### 叠加因素

- 数据量太少（26 条 / 60 条，官方推荐每任务 100–200 条）
- 数据太单一（单一站位、单一光照、首帧差异大）

#### ⚠️ 边界

**根因是靠证据链定位的，「换回同一台机器 / 重采数据后问题消失」这个闭环验证当时还没做完。** 答的时候要说这一层。

### Q24. 为什么把真机抓取失败归因至「站位变化引起的相机视角偏移」与「物体位置引起的左右手误判」？

这是**两个独立的失败模式**，各有各的证据链。

#### 失败模式 ①：站位变化 → 头相机视角偏移

**观测**：机器人相对桌子的站位不同时，抓取会失败。

**机制**：站位一变，**头相机看到的画面构图整体变化**（桌面在画幅中的位置、物体的像素坐标、透视）。头相机是唯一的第三人称视角，也是判断物体在哪的主要依据。

**为什么是「视角偏移」而不是「站位」本身**：机器人不知道自己站在哪——它没有全局定位输入。**站位只能通过图像影响模型。** 所以真正的失效通道是视角，站位是原因。这个区分决定了解法：**不需要标定站位，需要让训练数据覆盖多种站位对应的视角。**

**训练数据侧的对应事实**：那批数据是单一站位采的 → 模型只见过一种构图。

#### 失败模式 ②：物体侧向位置 → 左右手误判

**观测**：物体放在左边时，模型会出**右**手 → 抓不到。

**为什么这个错误是可以修的（而不是模型能力上限）**：做了一次数据侧检验——

```
对每条 episode:
    检测物体的连通域（blob）
    排除正中线附近的窄带（这一带本来就该左右都行）
    判断 blob 中心在左还是在右
    对照实际用了哪只手
```

结果：**排除正中线窄带后，18/23 条完全分离**——也就是「物体在哪边 → 用哪只手」这个规律**在视觉上是可学的**，不需要额外输入。

**手别的分布**：右 15 / 左 11 / 双手 3。**手别由物体位置决定 = 就近取手。**

**这个检验有两个直接产出**：
1. **prompt 不必带手别**（有些做法会在指令里写「用左手」，这里不需要——视觉信息足够）
2. **失败是数据覆盖问题**：左/右样本不均衡（15 vs 11），且总量太小

#### 所以采集方案是一一对应设计的

| 失败模式 | 对应的采集设计 |
|---|---|
| 站位变化 → 视角偏移 | **站位随机化**（多个不同站位） |
| 物体位置 → 左右手误判 | **物体左/中/右 = 35:30:35** |
| （鲁棒性）物体姿态单一 | 正放 / 倒放等多种摆放 |
| （控制变量）起始位姿 | **本轮固定**，见 Q28 |

### Q25. 还定位过哪些静默失败？

这些都不在简历上，但同属一类能力，被问到「还有别的例子吗」时用。

#### ① 网络组播未隔离 → 指令同时下发到多套系统

**机制**：DDS 默认组播 + 同一域 ID + 两张网卡同时在线（一张办公网、一张直连机器人）→ **控制指令同时发给真机和同网段其他人的仿真系统**，且读回的状态分不清来自谁。

**实测三种配置对照（节点数）**：

| 配置 | 可见节点 |
|---|---|
| 不锁网卡 | 85 个，含别人的仿真 + **3 个不同的运控节点** |
| 锁到直连口 | 85 个，**0 个仿真，恰好 1 个运控节点** ✅ |
| 锁到办公网 | 10 个 = 别人那套系统的全貌 |

**修法**：把 DDS 的网卡白名单锁到直连口 IP，并保证三处地址一致（网络 profile / DDS 配置 / 实际网卡）——**三者不一致时 DDS 会没有可用网卡且不报错**。

**附带一个查证方法论坑**：查节点列表的命令默认走后台 daemon，daemon 用**第一次调用时的环境**创建。换了 DDS 配置再查还是查同一个 daemon，**结论全错**。必须先停 daemon 再用免 daemon 模式查。

#### ② 相机服务未随主流程启动

腕相机的话题一开始**根本不存在**（查询报未知话题、零帧）。排查出来：腕相机由**另一个独立的相机服务**发布，不是主相机服务，而官方文档的相机话题总表里**根本不提它**（腕相机是选装件）。

→ 上机第一步固定加一条检查：该服务在不在，不在就先起。

#### ③ 图像通道序颠倒

解压缩出来是 **BGR** 而模型要 **RGB**。不转就是「颜色反了且完全不报错」——模型照样输出动作，只是全错。

同类的还有一处：头相机**物理倒装**需要 180° 旋转，而且**训练侧的转换脚本和部署侧的客户端必须做完全相同的旋转**，两边不一致同样是静默的。

#### ④ 底层重力补偿稳态误差 → 单向漂移

**现象**：推理一开始，肘部带着小臂持续往下抬。乱摆场景都复现 → 怀疑是系统性稳态误差而非场景不匹配。

**验证方法（值得讲的是这个方法）**：写一个**不含模型**的最小测试脚本，直接下发一个确定的指令，观测关节状态反馈，比对指令与实测的差值。

**结果**：差值显著，**肘部最大、肩部次之，左右臂误差符号相反、力矩为 0** → 典型的重力补偿问题。定位后转给运控团队修复。

> **用一个已知的确定指令去测系统的开环响应**，就能把「模型的锅」和「底层的锅」切开。

#### ⑤ 一个恒定不变的话题两次误导排查

排查遥操作链路时，某个看起来该是驱动源的话题**恒定不变**，两次把排查带偏。最后靠**与下游的相关性**（0.9995）才定位到真正的驱动源。

> **判断「谁是驱动源」要看与下游的相关性，不能看话题自身是否活跃。**

#### ⑥ 带宽取舍（不是失败，但是同类的实测替代估算）

原本按经验估压缩比 10:1，实测：

| | 裸流 | 压缩流 | 压缩比 |
|---|---|---|---|
| 头相机 | 75–80 MB/s（≈640 Mbps） | 3.13 MB/s（≈25 Mbps） | **27:1** |

三路合计 ≈40 Mbps，千兆口宽松 → **头相机订压缩流、腕相机订裸流**，实测三路都稳定 30Hz，**不必把客户端搬到机器人本体的计算单元上**。

### Q26. 80+ 条是怎么采的？

**自己戴 VR 手柄遥操作采的**，不是拿现成数据集。

- 8/17 先练操作（不熟练时采的不算）
- 8/18 采了 60 条 → 转换后 **59 条 / 12223 帧 / 30fps** 可用
- 8/20 按新方案重采了 20+ 条

1. 遥操作服务跑在**另一台计算单元**上，连错 IP 时机器人完全没反应
2. 末端执行器类型配置成了**灵巧手**，需改成夹爪，机器人才跟随人的动作
3. 手机 App 版本落后于机器人固件版本 → **没有数采模式**，需要重新申请下载

### Q27. 35:30:35 这个配比的依据？

**直接来自 Q24 的失败模式 ②。**

已知事实：
- 手别由物体位置决定（就近取手），且**视觉上可学**（18/23 完全分离）
- 现有数据手别分布 **右 15 / 左 11 / 双手 3** → 左右不均衡
- 正中线附近是**本质歧义带**（左右手都合理）

设计：
- **左 35 / 右 35** —— 强制左右平衡，消除现有数据的右手偏置
- **中 30** —— 覆盖歧义带。这一档不是为了教模型选哪只手，而是让它在歧义带里**至少输出一个可执行的决策**，而不是在两个模式之间抖

**为什么 100 条**：官方指导每任务最少 100 条（窄任务约 30），推荐 200+。现有 59 条已证明「够跑通管线、不够训策略」。

### Q28. 为什么固定起始位姿？

**控制变量。**

已知的失败因子至少三个：站位、物体位置、起始位姿。这一轮同时放开三个的话，采完仍然分不清是哪一个在起作用——**样本量不够支撑三因子的覆盖**（100 条分给三个因子，每个格子只剩几条）。

所以：
- 放开**站位**和**物体位置**（这两个有明确证据链，见 Q24）
- **固定起始位姿**

**并且固定起始位姿本身是有独立收益的**：它让复位这道安全门更可靠（复位姿态就是那个固定的起始位姿，见 Q19），也让首帧分布更集中——而「首帧差异大 → 需要更多数据才能泛化」是从第一批数据里学到的教训。

**这不是「没做完」，是本轮刻意不动的变量。** 下一轮再放开。

### Q29. 采集规范是怎么来的？

**从第一版训练的失败里反推出来的，不是抄文档。**

第一版 26 条数据训完，回看数据集发现四类污染源，逐条对应一条规范：

| 数据里发现的问题 | 对应规范 | 依据 |
|---|---|---|
| 数据量少时腰不该动，但数据里腰在动 | **腰 + 下肢锁死** | 单条 episode 内腰的偏航摆到 35.9° |
| 存在「跟随抓取」（一只手抓时另一只手也抬） | **剔除该类数据** | 这个污染**直接在推理时复现了**（8/19 观测到空闲手偶发抬起） |
| 首帧差别大 | **首帧尽量一致** | 差异越大需要越多数据才能泛化 |
| 光照训推不一致 | **训推同环境** | — |
| 总量不足 | **每任务 100–200 条** | 26 条、60 条都验证过不够 |

**「跟随抓取」这条最有说服力**——它是「数据里的污染 → 推理时的具体异常行为」一一对应上的，不是猜的。

⚠️ **一个反直觉的事实要记住**：虽然这是抓取任务、只有一只手在抓，但**两只臂始终都在动**，非抓取臂 ROM 均值 19.46° vs 抓取臂 31.39°。**不要把它说成「单臂任务、没有双臂协同」。** 这也意味着「把空闲臂钉死」不是免费的（见 Q31）。

## Part G — 简历上没写但会被问的

### Q30. 那个「17.8% 训练样本被静默污染」的框架缺陷是怎么发现的？

（这一条从简历删掉了，因为术语密度太高、和上下文域不一致；但它是追问环节含金量最高的一项。）

#### 一句话

**是读出来的，不是调出来的**——在跑训练之前就发现了，不是靠指标异常反查。

#### 机制

配置里让视觉观测取「当前帧 + 1 秒前那一帧」，即时序偏移 `[-30, 0]`。取数实现是：

```
indices_to_load = [step_index + delta for delta in delta_indices]
if allow_padding:                                    # 默认 False
    indices_to_load = clamp(indices_to_load, 0, len(episode) - 1)
```

而训练窗口起点是 `arange(0, ...)`，**从 0 开始**。于是 `step_index = 0` 时算出 `[-30, 0]`——`-30` 是**负索引**。

**pandas 的 `.iloc[-30]` 不报错**，它按 Python 语义返回**倒数第 30 行**。

```
step= 0   indices=[-30, 0]   实际取到帧号=[138, 0]    ← 「1 秒前」是 episode 末尾
step=29   indices=[ -1,29]   实际取到帧号=[167, 29]
step=30   indices=[  0,30]   实际取到帧号=[  0, 30]   ← 从这里才正常
```

**每条 episode 的前 30 个训练窗口，模型看到的「一秒前」其实是任务已完成之后的画面。**

#### 为什么是静默的

三层都不会响：
- pandas 负索引合法 → 不抛异常
- 张量形状完全正确（还是 2 帧）→ 下游拼接不崩
- loss 照样单调下降 → 训练曲线看不出异常

#### 发现过程

1. **触发点：我们的配置刻意偏离了官方示例。** 用双帧的依据是 checkpoint 里 8 个预训练本体**全部**用负索引（-15/-20/-30），而官方微调示例用的是单帧 `[0]` → **我们走上了一条官方示例不覆盖的代码路径。**
2. **为了写配置去读取数实现，读到 `if allow_padding:` 就停住了。** 一段防御代码默认关闭，等于作者在说「这里有坑，但我这条路径不踩」——**那就要问「谁会踩」。**
3. **顺着查采样起点**，确认负索引是**必然发生**而不是罕见边界。
4. **写专项脚本实测复现**，关键设计是**走真实的取数函数**（不自己重写取数逻辑，否则复现的是自己的想象），然后逐字节比对：

| 设置 | step 0 取到的历史帧 | 判据 |
|---|---|---|
| `allow_padding=False` | 逐字节 == `iloc[-30]` | bug 复现 |
| `allow_padding=True` | 逐字节 == `iloc[0]` | 钳制生效 |
| 两者在 step=50（安全区） | **逐字节相同** | 修法不扰动正常路径 ← 反证 |

5. **量化影响面**：遍历 59 条 episode 累加 → **1770/9922 = 17.8%**

#### 责任归属要说准

| 事实 | |
|---|---|
| 钳制保护**存在** | ✅ |
| 但默认 **False** | |
| 微调配置**不暴露**这个字段，官方 CLI 够不到 | ← **要害** |
| 官方微调示例用单帧，所以永不触发 | |
| 但**他们自己 8 个预训练本体全部用负索引** | ← **要害** |

**准确的表述是：官方微调链路上一个默认开启、无法通过官方接口关闭的静默数据污染。** 不是「NVIDIA 写错了」。修法是自写 launcher 把字段透出来。

#### ⚠️ 两条边界

- **17.8% 是我们数据集的数字**（59 条、H=40、偏移 -30），episode 越短占比越高，不是普适值
- **不能说它解释了任何已观测到的性能问题**——这是预防性发现，靠指标几乎不可能查到它

### Q31. ⚠️ 「块内平滑与下发限幅」具体做了什么？

**这一项需要在答之前确认状态。** 当前代码里的实际情况：

| 层 | 抖动来源 | 状态 |
|---|---|---|
| **块间** | 换块时新旧轨迹跳变 | ✅ **RTC 跨块对齐已实现**（见 Q16） |
| **块内** | 模型输出在相邻步上不连续 | ⚠️ 未实现 |
| **下发层** | 无速度/加速度约束 | ⚠️ 只有**关节限位钳制**（`clip(arm, 下限, 上限)` + 累计被钳次数），**没有速率限制** |

**如果块内平滑和速率限幅还没做，简历上这半句要改掉或删掉**——它是全篇唯一一处纯实现描述、不带任何数字或结论，一问「怎么做的、效果如何」就露。

#### 如果要做，方案是这样的

```
# 下发层速率限幅（伪代码）
target ← clip(action, 关节下限, 关节上限)            # 已有
Δ ← target − 上一次下发的目标
Δ ← clip(Δ, −v_max/hz, +v_max/hz)                   # 新增：速度限幅
target ← 上一次下发的目标 + Δ
```

**注意 v_max 的选取有依据可循**：复位斜坡用的是 15°/s，而数据里的实际关节速度分布可以直接统计出来——用数据的分位数定 v_max，比拍一个数字好。

#### 关于「空闲臂规整」——建议先不写进简历

上一轮讨论的结论是：**它不是免费的**。

数据里非抓取臂 ROM 均值 19.46°、抓取臂 31.39°——**两只臂始终都在动**。把空闲臂重写成固定角度等于人为改掉这部分动作分布：

| 做法 | 代价 |
|---|---|
| **数据侧钉死** | 训练分布变干净，但模型再也学不到双臂协同，将来做需要双手配合的任务要重采 |
| **推理侧钳制** | 训练分布不动，只在下发时压住空闲臂；可逆、可开关，但治的是症状 |

**建议顺序：先做推理侧钳制**，因为它可逆、能立刻验证「抖动是否真由空闲臂贡献」；确认有效再决定要不要动数据。

### Q32. 两条链路「效果差不多」该怎么说？

**要主动加限定，否则会被问穿。**

| | π0.5 | GR00T N1.7 |
|---|---|---|
| 视觉帧 | 单帧 | 双帧（1 秒历史） |
| action horizon | 32 | 40 |

### Q33. GR00T 为什么用 NEW_EMBODIMENT 而不是那个同构的预训练本体槽位？

GR00T 的预训练本体里有一个是**双臂 7-DoF + 3-DoF 腰**（另一家的人形平台），与本体拓扑一致。理论上可以从那个槽位初始化。

**没有这么做，是明确的决策**：

- 它的动作是末端位姿（EEF）+ 相对关节，且腰是绝对动作，与我们的口径不同
- 从别人的本体槽位初始化，等于引入一次隐式的跨本体迁移——**这本身是另一个课题**，会把「GR00T 在我们数据上行不行」这个问题污染掉

**代价要承认**：选 NEW_EMBODIMENT 意味着那套投影层是**随机初始化从头学**。「本体拓扑匹配」这个优势目前只体现在骨干和动作头上，**不体现在 projector 上**。

### Q34. 这个项目最大的失误 / 重做会怎么改？

诚实的三条：

#### ① 数据量的判断慢了

一直到 8/14 才总结出「每任务 100–200 条、首帧一致、腰不能动」这套规范。**在此之前用 26 条数据反复调模型、查代码、做消融**——花在「是不是代码有问题」上的时间，如果早一点判定「数据量根本不够」，可以省下来。

**重做的话**：先按官方下限（100 条）采够再开始训，而不是拿 26 条边训边查。

#### ② 验证集切得太晚、太小，而且后来干脆没切

26/2 的划分只够回答「链路对不对」。后来 59 条全量进训 → 那批完全没有泛化指标。**这是明知不对但因数据太少而妥协的决定**，重做的话应该在数据量上去之后立刻补上。

#### ③ 部署机与训练数据机不同这件事，本该更早排除

「腕相机看自己的夹爪，尺度差 1.45 倍」这个检查**成本极低**（一张图、一个已知刚性物体），但它是在幅度坍塌查了好几天之后才做的。

**可迁移的教训**：跨机器部署时，**第一步就该用一个视野里的已知刚性物体核对相机尺度**——这是最便宜的「是不是同一台机器」检查。

### Q35. 下一步要做什么？

1. **补齐数据**：按 Q27 的方案采 100 条（站位随机化、左/中/右 35:30:35、多种摆放），重训
2. **切留出集**，把泛化指标补上
3. **量真实推理延迟**，然后才能回答 RTC 的抖动改善（Q17）
4. **统计抓取成功率**（固定协议、N 次重复），这是目前最缺的数字
5. **补块内平滑与下发速率限幅**（Q31）
6. A/B 项：GR00T 的本体槽位初始化（Q33）、π0.5 头相机裁 4:3 vs 补边
