# BAAI 大脑大模型赛道面试题

> 相关材料：[[11-17智源BAAI大脑大模型赛道决赛答辩-浅试团队.pdf]]

比赛主线可以概括为：

> 原始数据标准化与打分 → 生成并复核结构化 CoT → CoT-SFT → 构造偏好对 → DPO。

但有两个关键修正：

- CoT 转换后还要再质检一次，因为错误通常发生在“转换”环节。
- Skywork Reward 用于数据粗排；DPO 直接使用 `chosen/rejected`，不需要再训练奖励模型。

---

## 1. 数据打分具体怎么实现

推荐采用“硬规则 + VLM Judge + Reward 排序”三层流程。

### 1.1 执行逻辑

```
硬规则不通过                    → 直接删除
Judge 评分 1–2                 → 删除
Judge 评分 3                   → 修复后重新评分
Judge 评分 4–6                 → 进入候选池
同分样本按 Skywork Reward 排序 → 按任务类型分桶抽样
```

Skywork 的输入是“媒体 + 问题 + 候选回答”，输出 value head 的连续 reward。该值只适合相对排序，不应直接映射成 1–6 分；最好在同一数据集、同一任务类型内部做 percentile 排名。[官方模型卡给出了完整的 value-head 取分方式](https://huggingface.co/Skywork/Skywork-VL-Reward-7B)。

### 1.2 精确 Judge Prompt

```
你是具身多模态训练数据质检器。

你将收到：
- media：图像或视频帧
- dataset：数据集名称
- task_type：任务类型
- source_annotation：原始可信标注
- instruction：训练指令
- input：模型输入
- candidate_output：待审核回答

请判断 candidate_output 是否适合用于监督微调。

审核规则：
1. 只依据 media 和 source_annotation，不补充无法验证的事实。
2. 原始标注和仿真状态的优先级高于生成文本。
3. 检查目标物体、动作、空间关系和时间范围是否一致。
4. 规划任务检查对象是否存在、前置条件是否满足、顺序是否可执行。
5. 检查 candidate_output 是否满足规定的 JSON 或答案格式。
6. 如果核心结论没有证据支持，最高只能评 3 分。
7. 不因回答更长或表达更流畅而提高分数。

评分标准：
1：媒体缺失、字段损坏或输出无法解析。
2：媒体和任务有效，但核心物体、关系、动作或答案错误。
3：基本相关，但证据不足、推理不完整或计划不可执行。
4：核心内容正确，仅有轻微冗余或格式问题。
5：事实正确、证据充分、步骤合理且格式合规。
6：满足 5 分，并覆盖复杂关系、长尾类别或高价值规划能力。

处理规则：
- 1–2 分：drop
- 3 分：repair
- 4–6 分：keep

只输出严格 JSON：
{
  "score": 1,
  "hard_fail": false,
  "checks": {
    "grounding": "pass|fail|unsupported",
    "relevance": "pass|fail",
    "executability": "pass|fail|na",
    "format": "pass|fail"
  },
  "evidence": ["简短列出依据"],
  "issues": ["简短列出问题"],
  "decision": "keep|repair|drop"
}
```

实际调用建议使用 `temperature=0`，并对 JSON 做解析校验。

### 1.3 真实数据集示例：EPIC-KITCHENS

官方真实记录：

```
{
  "narration_id": "P01_01_0",
  "video_id": "P01_01",
  "start_frame": 8,
  "stop_frame": 202,
  "narration": "open door",
  "verb": "open",
  "noun": "door"
}
```

这些字段可以在 [EPIC-KITCHENS 官方注释仓库](https://github.com/epic-kitchens/epic-kitchens-100-annotations) 中核对。

如果转换结果是：

```
{
  "action": "close",
  "object": "door"
}
```

Judge 应输出：

```
{
  "score": 2,
  "hard_fail": false,
  "checks": {
    "grounding": "fail",
    "relevance": "pass",
    "executability": "na",
    "format": "pass"
  },
  "evidence": [
    "源标注 verb=open、noun=door、frames=8-202"
  ],
  "issues": [
    "candidate_output 将 open 错写为 close"
  ],
  "decision": "drop"
}
```

## 2. 转换成 CoT 具体怎么实现

核心不是让大模型自由扩写，而是让强 VLM 根据图像和可信标注，生成“最短、结构化、可核验”的推理轨迹。

需要区分：

- `audit_evidence`：供数据审核使用，不参加 SFT。
- `assistant_output`：真正作为模型训练目标。

### 2.1 精确 CoT 生成 Prompt

```
你是具身多模态监督数据转换器。

输入包括图像或视频、可信源标注和任务类型。
你的任务是生成一条结构化 CoT 监督样本，而不是重新标注数据。

生成规则：
1. 所有结论必须能够由媒体或 source_annotation 支持。
2. 不得增加源标注中不存在、媒体中也无法确认的物体、动作或因果关系。
3. 每个 reasoning step 只完成一个操作。
4. 空间任务优先使用 ground、compare_position、infer_relation。
5. 视频任务优先使用 temporal_localize、observe_state_change、identify_action。
6. 规划任务使用 check_precondition、select_action、predict_effect，最多生成 3–5 个高层步骤。
7. 简单关系题只生成 1–2 个必要步骤，不强行延长 CoT。
8. audit_evidence 只用于审核；assistant_output 必须能够由部署时的图像或视频输入推断。
9. 如果证据不足，输出 valid=false，不得猜测。

只输出严格 JSON：
{
  "valid": true,
  "instruction": "给学生模型的问题",
  "audit_evidence": [
    {
      "source_field": "源字段名称",
      "fact": "直接支持答案的事实"
    }
  ],
  "assistant_output": {
    "observations": ["从媒体中可观察到的必要事实"],
    "reasoning_steps": [
      {
        "step": 1,
        "operation": "规定操作名称",
        "result": "本步骤结论"
      }
    ],
    "final_answer": "最终答案"
  }
}
```

### 2.2 真实数据集示例：Visual Genome

材料中的真实场景标注：

```
{
  "region_description": "a man and a woman sit on a park bench along a river",
  "relationships": [
    ["man", "sits on", "bench"],
    ["man", "in front of", "river"],
    ["woman", "sits on", "bench"]
  ]
}
```

转换结果：

```
{
  "valid": true,
  "instruction": "根据图像，男子相对于河流位于什么位置？",
  "audit_evidence": [
    {
      "source_field": "relationships",
      "fact": "man in front of river"
    }
  ],
  "assistant_output": {
    "observations": [
      "图中可以定位到男子和河流"
    ],
    "reasoning_steps": [
      {
        "step": 1,
        "operation": "ground",
        "result": "目标是男子，参照物是河流"
      },
      {
        "step": 2,
        "operation": "infer_relation",
        "result": "男子位于河流前方"
      }
    ],
    "final_answer": "男子在河流前方"
  }
}
```

写入 LLaMA-Factory 时，只把 `instruction + assistant_output` 作为训练内容：

```
{
  "conversations": [
    {
      "from": "human",
      "value": "<image>根据图像，男子相对于河流位于什么位置？"
    },
    {
      "from": "gpt",
      "value": "{\"observations\":[\"图中可以定位到男子和河流\"],\"reasoning_steps\":[{\"step\":1,\"operation\":\"ground\",\"result\":\"目标是男子，参照物是河流\"},{\"step\":2,\"operation\":\"infer_relation\",\"result\":\"男子位于河流前方\"}],\"final_answer\":\"男子在河流前方\"}"
    }
  ],
  "images": ["visual_genome/xxx.jpg"]
}
```

`audit_evidence` 保存在旁路 JSONL 中，用于复核，不能喂给学生模型，否则会造成标注泄漏。LLaMA-Factory 的多模态格式要求 `<image>` 数量与 `images` 路径数量一致，[官方数据格式说明在这里](https://github.com/hiyouga/LlamaFactory/tree/main/data)。

CoT 生成后，再用第 1 部分的 Judge Prompt 评分一次，只有 4–6 分样本进入 SFT。

## 3. DPO 具体怎么实现

DPO 的对象不是单个分数，而是同一输入下的一对回答：

```
prompt + chosen（正确计划）+ rejected（错误计划）
```

标准做法是：

1. 使用 CoT-SFT checkpoint 作为初始模型和 reference model。
2. 从成功 episode 提取 `chosen`。
3. 对 chosen 注入一个有实际影响的错误生成 `rejected`，例如调换顺序、删除前置条件、替换对象。
4. 在相同初始状态下执行两条计划。
5. 只保留 `chosen` 成功且 `rejected` 失败的样本。
6. 两边保持相同 JSON 结构和近似长度，避免模型学习长度或文风捷径。

DPO 会提高 chosen 相对于 rejected 的概率，同时用 SFT 模型约束更新幅度，不需要单独训练奖励模型。[原始 DPO 论文也建议使用 SFT 模型作为 reference](https://arxiv.org/abs/2305.18290)。

### 3.1 真实环境示例：AI2-THOR

假设 AI2-THOR 初始状态中：

```
{
  "Apple": {
    "visible": true,
    "pickupable": true,
    "isPickedUp": false
  },
  "Fridge": {
    "visible": true,
    "openable": true,
    "isOpen": false
  }
}
```

目标：把苹果放入冰箱。

DPO 数据：

```
{
  "conversations": [
    {
      "from": "human",
      "value": "<image>目标：把苹果放入冰箱。请输出可执行的高层计划。"
    }
  ],
  "chosen": {
    "from": "gpt",
    "value": "{\"plan\":[{\"action\":\"OpenObject\",\"object\":\"Fridge\"},{\"action\":\"PickupObject\",\"object\":\"Apple\"},{\"action\":\"PutObject\",\"object\":\"Apple\",\"receptacle\":\"Fridge\"}]}"
  },
  "rejected": {
    "from": "gpt",
    "value": "{\"plan\":[{\"action\":\"PickupObject\",\"object\":\"Apple\"},{\"action\":\"PutObject\",\"object\":\"Apple\",\"receptacle\":\"Fridge\"},{\"action\":\"OpenObject\",\"object\":\"Fridge\"}]}"
  },
  "images": ["ai2thor/FloorPlan1/frame_000.png"]
}
```

两条计划都在相同场景重放：

- chosen：所有 `lastActionSuccess=true`，最终 `Apple.parentReceptacles` 包含 Fridge。
- rejected：向关闭的冰箱执行 `PutObject` 时失败。

AI2-THOR 官方明确提供 `lastActionSuccess`、对象状态和容器关系；动作失败时环境状态不会改变，因此可以作为偏好标签真值。[AI2-THOR 环境状态文档](https://ai2thor.allenai.org/ithor/documentation/environment-state/)。

### 3.2 LLaMA-Factory 配置

`dataset_info.json`：

```
{
  "ai2thor_dpo": {
    "file_name": "ai2thor_dpo.json",
    "formatting": "sharegpt",
    "ranking": true,
    "columns": {
      "messages": "conversations",
      "chosen": "chosen",
      "rejected": "rejected",
      "images": "images"
    }
  }
}
```

LLaMA-Factory 官方要求偏好数据包含 `chosen`、`rejected` 并设置 `ranking=true`。[官方 Preference Dataset 格式](https://github.com/hiyouga/LlamaFactory/tree/main/data)。

适合本项目的起始配置：

```
model_name_or_path: /path/to/cot_sft_merged
stage: dpo
do_train: true

finetuning_type: lora
lora_target: all
lora_rank: 16

dataset: ai2thor_dpo
template: qwen2_vl
cutoff_len: 2048

pref_loss: sigmoid
pref_beta: 0.1

learning_rate: 5.0e-6
num_train_epochs: 1.0
per_device_train_batch_size: 1
gradient_accumulation_steps: 8
lr_scheduler_type: cosine
warmup_ratio: 0.1
bf16: true
```

`pref_beta=0.1、sigmoid、5e-6 LoRA` 是稳妥起点，也与 [LLaMA-Factory 官方多模态 DPO 示例](https://github.com/hiyouga/LlamaFactory/blob/main/examples/train_lora/qwen3vl_lora_dpo.yaml)一致。如果继续全参 DPO，学习率应降到约 `5e-7～1e-6`。

最终最准确的项目表述是：

> 我们先对原始和转换后样本做规则校验、VLM 分档及 Reward 粗排；再利用源标注生成可验证的结构化 CoT，完成 SFT；最后从 AI2-THOR 成功轨迹和可执行失败轨迹中构造 chosen/rejected，在 SFT checkpoint 上进行 DPO。
